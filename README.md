# Invoice-to-payment reconciliation with pandas

A small, tested Python tool that matches vendor invoices against the payments received,
classifies every discrepancy, and produces a recovery report a non-technical reader can act on.

It works on the kind of data real payment files contain: invoice numbers written five different
ways, vendor codes in mixed case, amounts as text (`"1,234.50"`, `"(25.00)"`), split payments,
chargeback reversals, several currencies with weekly exchange rates, and payments that cannot be
attributed with certainty.

> All data in `data/sample/` is fictional and generated by `scripts/generate_sample_data.py`
> (fixed seed, fully reproducible). No real company or customer data is used.

## What it does

1. **Cleans** invoices and payments (`conciliacion/normalize.py`): canonical invoice ids
   (`INV-001005`, `inv1005`, `Factura #01005` all become `1005`), vendor codes, amounts,
   dates, and drops exact duplicate invoice rows.
2. **Converts currencies** (`conciliacion/fx.py`): each row takes the latest rate published on
   or before its own date with `pd.merge_asof`. A row with no rate stays `NaN` and the run stops,
   so a missing rate is never guessed.
3. **Matches** payments to invoices (`conciliacion/reconcile.py`):
   - on `(vendor_id, invoice_key)` when the payment has a vendor code;
   - on `invoice_key` alone when it does not, **only if exactly one invoice has that key**.
     If two vendors share the number, the payment is flagged `AMBIGUOUS` and assigned to nobody:
     a wrong match would hide a real underpayment.
4. **Classifies** every invoice, comparing amounts **in the invoice's own currency** so that
   exchange-rate movement is never reported as an underpayment:

   | Status | Meaning | Recoverable |
   |---|---|---|
   | `PAID` | payments add up to the invoice (±0.01) | 0 |
   | `UNDERPAID` | paid less than invoiced | the gap |
   | `UNPAID` | no payment found | the full amount |
   | `REVERSED` | paid, then reversed back to zero | the full amount |
   | `OVERPAID` | paid more than invoiced | 0 (flagged for review) |

   Payments that cannot be assigned go to a separate exceptions file as `UNMATCHED_PAYMENT`
   or `AMBIGUOUS`.
5. **Reports** (`conciliacion/report.py`) to `output/`:
   `invoice_results.csv`, `recovery_claims.csv` (sorted by amount), `payment_exceptions.csv`,
   `vendor_summary.csv`, and `invoice_results.parquet`.

## Run it

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows; use .venv/bin/activate on macOS/Linux
pip install -r requirements.txt

python scripts/generate_sample_data.py      # writes data/sample/*.csv
python -m conciliacion --data data/sample --out output
python -m pytest                            # 33 tests
```

Sample run:

```
Invoices: 122  |  Payment exceptions: 3
PAID 71 | UNPAID 21 | UNDERPAID 15 | REVERSED 9 | OVERPAID 6
Recoverable: USD 61,768.69
```

## Tests

`pytest` covers id normalization edge cases, amount parsing, exchange-rate lookup, every status,
the ambiguous-match rule, the "exchange-rate drift is not an underpayment" rule, money
conservation (`paid + gap = invoiced`), and an end-to-end check that the status counts equal
the scenarios planted by the generator.

## Pandas used

`read_csv` with `dtype=str`, `map`, `where`, `drop_duplicates`, `merge` (left joins with
candidate counting to avoid row duplication), `merge_asof` (`by=`, `direction="backward"`),
`groupby().agg()` with named aggregations, `crosstab`, `value_counts`, `to_parquet`.

is covered by a test.
